## 1. 这份文档要解决什么

[设计文档](./group-mesh-design.md) 定义了"要做成什么样"，但没有回答"先做什么、
每一步怎么验收、哪些地方会踩坑"。本文补上这三件事，并**如实标注当前实现与设计
文档之间的偏离** —— 偏离比缺功能更危险，因为缺功能看得见，偏离看不见。

一句话概括当前进度：**设计文档 §4（身份）、§5（名单）、§6（共享与 ACL）、§7（注册）
的骨架已经可运行，并在 Windows 与 Linux 两台真机上完成了加密传输验证。**
游戏面（§9）、语音（§8.3）、Android 轻客户端（§11.2）、回收站（§6.4）、内容寻址
传输（§10）尚未开始。

## 2. 分层与边界

```
   ┌─────────────────────────────────────────────────────────┐
   │ shell/backend/            壳：Flask 路由、令牌、设置存储  │
   │   （§12 要求的主体上下文尚未提供 → P1 的阻塞项）          │
   └───────────────────────────┬─────────────────────────────┘
                               │ PluginBase / register_api
   ┌───────────────────────────▼─────────────────────────────┐
   │ plugins/group-mesh/       插件层（v0.1 骨架）             │
   │   backend/main.py         身份/团体/共享项/节点 的 API     │
   │   frontend/               状态页与操作入口                │
   └───────────────────────────┬─────────────────────────────┘
                               │ import shell.groupmesh（普通包导入）
   ┌───────────────────────────▼─────────────────────────────┐
   │ shell/groupmesh/          协议内核（壳层包，不依赖 Flask） │
   │   crypto_prims  records  identity  roster                │
   │   shares  registry  noise  transport  node  client  cli   │
   └─────────────────────────────────────────────────────────┘
```

**内核住在 `shell/groupmesh`**（与 `shell/backend`、`shell/frontend` 并列），
而不是 `tools/`，也不是某个插件内部。三条理由，都是结构性的：

1. **它是壳层能力，不是工具脚本**。设计文档 §12 要求的"凭据→主体映射"与
   "插件以受信方式读取主体"本身就是壳的职责，内核与它们是同一层的东西。
2. **它要被多个插件复用**。设计文档 §1.2 把 group-mesh 定为**核心插件**，
   文件传输、游戏联机、语音是依赖它的 Companion 插件。若把内核塞进
   `plugins/group-mesh/` 的私有目录，那些 Companion 就得依赖另一个插件的内部
   结构（`get_dependency()` 暴露的是插件实例，不是它的子模块路径）。
3. **它必须能脱离 GUI 独立跑**。内核不 import Flask / pywebview（实测确认
   `python -m shell.groupmesh.cli selftest` 只加载标准库与 pycryptodome），
   因此协议错误与插件集成错误可以分开定位，跨机联调也不必先在两台机器上
   装好并启动图形界面。

放在 `shell/backend/` **下面**是不行的：`shell/backend/__init__.py` 会 eagerly
import `file_server`，从而把整个 Flask 栈拖进来，"独立跑"这条就没了。
因此它是 `backend/` 的**兄弟**而不是子目录。

插件这一层于是只剩三件事：解析数据目录、把内核能力转成 API、管理监听线程；
它用普通 `import shell.groupmesh...` 就能拿到内核，不需要往 `sys.path` 里塞路径，
也不需要"内核缺失时降级"这种分支 —— 打包阶段由 `HIDDEN_IMPORTS` 保证内核随包分发，
缺失会在 `check_packaging` 门禁就被拦住，而不是等到用户点按钮。

每个阶段都以**可复核的命令**结尾，不用"看起来能跑"作为完成标准。

### P1 —— 补上设计文档 §12 的壳侧缺口（阻塞后续阶段）

设计文档 §12 列了 6 项壳侧改造，其中第 1、2 项是**授权语义的前提**：

| # | 项 | 为什么阻塞 |
| --- | --- | --- |
| 1 | 凭据到主体的映射 | 没有它，"谁在调用"只能靠插件猜；当前实现退化为"本机身份即操作者" |
| 2 | 插件以受信方式读取主体 | 同上；且必须走 `ContextVar`，不能从请求参数读 |

另 4 项（数据路由授权、文件根支持远端共享、设置写入限权、`minShellVersion` 运行时校验）
可以与本阶段并行。

**验收标准**：插件能通过 `self.current_principal()` 拿到**由壳注入**的主体标识，
且该值无法被请求参数影响（用一个伪造 `principal` 字段的请求验证它被忽略）。

## 4. 与设计文档的已知偏离

**这一节是本文最重要的部分。** 每一条都必须在进入生产前收敛，否则就是"文档说 A、
代码做 B"。

### 4.1 私钥是明文落盘的（高危）

* 设计文档 §4.1：「设备私钥不导出，由操作系统提供的密钥存储保存（Windows 为 DPAPI，
  Android 为 Keystore）」。
* 当前实现：`identity/principal.json` 与 `identity/devices/<id>.json` 中 **base64 明文**，
  仅靠目录 0700 / 文件 0600 保护，并申报为受保护路径（不会被文件服务端出去）。
* 影响：任何能读到该目录的进程都可冒充该主体。
* 收敛路径：Windows 走 DPAPI（`win32crypt` / `CryptProtectData`），Linux 走 keyring
  或至少一个口令派生的 KEK。**应在 P2 优先做。**

### 4.2 Noise 状态机是自写的，不是"现成实现"（高风险）

* 设计文档 §4.4：「握手使用 Noise 框架的现成实现，不自行设计密码学组合」。
* 当前实现：只复用已审计的**原语**（pycryptodome），按 Noise 规范 §5.3/§7.5 自写
  状态机。这样做的安全性来自"原语正确 + 状态机照规范写"，**不是**来自长期审查过的
  协议实现 —— 这个区别不应被含糊掉。
* 佐证：本次实现中 XX 的 token 顺序与 nonce 延续规则**确实错了三次**（见 §5.1），
  每次的表现都只是对端一句 `MAC check failed`。
* 收敛路径：换成 `noiseprotocol` 或 `snow` 等价实现，并**用 Noise 官方测试向量**
  验证，而不是只验"两端能互通"。这一步应在 P2 之前完成。

### 4.3 传输层没有换出密钥（forward secrecy 的实际强度）

* 设计文档 §4.4：「每条会话使用临时密钥，具备前向安全」。
* 当前实现：握手本身有前向安全（临时密钥），但**长连接的传输密钥在整条连接生命周期内
  不轮换**，也没有消息数上限（除 `2^64` 的 nonce 上限外）。
* 影响：单条超长连接泄露一把传输密钥，该连接内全部内容可解。
* 收敛路径：按消息数或字节数触发 `Rekey()`（Noise §11.3），或限制单连接时长后强制重握手。

### 4.4 删除是物理删除，没有回收站（与 §6.4 直接冲突）

* 设计文档 §6.4：删除分两段——先进应用级回收站（默认 30 天），再移交系统回收站。
* 当前实现：`Node._op_delete()` 直接 `os.remove()`，并在应答里明确写
  `'note': 'MVP 为物理删除，应用级回收站未实现'`。
* 影响：误删不可恢复，而这正是设计文档要防的场景。
* 收敛路径：P2 实现应用级回收站（按共享项建 `.recycle/` 并记录元数据），
  再按 §6.4 的平台表接系统回收站。

### 4.5 身份签名与 Noise 静态密钥是两把密钥

* 设计文档 §4.3：「同一个设备密钥同时用于应用面握手与共享节点注册，不维护第二套账号」。
* 当前实现：设备持有 **Ed25519 签名密钥** 与 **派生出的 X25519 握手密钥**，
  两者由同一个 32 字节种子确定性派生（`dh_keypair_from_sign_seed`），
  并在握手中用**设备绑定证明**把二者绑在一起。
* 这是必要的偏离：Ed25519 私钥不是合法的 X25519 标量，直接当 DH 用会让**双方算出
  不同的共享密钥且都不报错**（见 §5.2）。从"账号数量"的角度仍然只有一套身份材料，
  但不满足"同一把密钥"的字面表述。
* 收敛路径：更新设计文档 §4.3 的措辞，明确"同一份身份种子，派生两把用途分离的密钥"，
  或者改用能同时用于签名与 DH 的曲线（如 Ed25519 的 `ed25519→curve25519` 双向映射，
  但那会牺牲与标准 Ed25519 的互通性）。

### 4.6 IPv4 是可达性兜底，主路径仍是 IPv6（已实测）

* 设计文档 §1.3：非目标含「无公网 IPv6 的使用者 —— 不提供 IPv4 NAT 穿透或公共中继兜底」。
* 实测条件（2026-09-15）：**两端都有全局 IPv6**。

  | 主机 | 全局 IPv6 | IPv4 |
  | --- | --- | --- |
  | Windows 192.168.31.4 | `2409:8a60:2abf:f5c0:6140:2c24:b049:f04c`（另有临时地址 `…:9401:5ed0:7e8d:95c0`） | 192.168.31.4/24 |
  | Linux 192.168.31.16 | `2409:8a60:2abf:f5c0:94b8:7fff:fe0a:e9f0`（`dynamic mngtmpaddr`，即 RFC 7217 稳定隐私地址） | 192.168.31.16/24 |

* 已用 `tools/ipv6-test.ps1` 完成**纯 IPv6** 联调：Linux 绑定全局 IPv6，Windows 用
  `[2409:…]:19444` 连接，700 KB 文件 sha256 两侧一致，越权与越界同样被拒，
  注册记录里写入的是该全局 IPv6 端点。
* 那么 IPv4 支持是什么定位：不是"额外提供的穿透能力"，而只是**同一可达网段内的
  地址族兜底**。双方在同一局域网时 IPv4 也能直连，代码因此对两个地址族都不设限；
  它不引入任何 NAT 穿透或中继，所以与 §1.3 的非目标不冲突。
* 仍然成立的边界：**跨公网**能否直连取决于运营商是否放行入站高位端口
  （§14 待实测项 1）。本文档所验证的是"同网段、地址族为 IPv6"，
  并不等于"公网可达"。

### 4.6.1 自动地址选择会把临时地址也当成端点（待修）

§7.4 明确要求「监听套接字与注册记录中的端点必须使用**稳定地址**，不使用
Windows 默认启用的 RFC 4941 临时地址，后者会轮换」。

当前实现 `registry.local_addresses()` **做不到这一点**：它只能排除回环与链路本地，
标准库拿不到"这个地址是否为 RFC 4941 临时地址"这一信息。实测中 Windows 侧确实
同时存在稳定地址与临时地址，因此 `serve` 在不显式指定 `--bind` 时会把两者都写进
注册记录 —— 临时地址轮换后，那条端点就失效了。

收敛路径（P1）：

1. 显式指定 `--bind` 到稳定地址（当前可用的规避手段）；
2. Windows 上用 `GetAdaptersAddresses` 的 `Temporary` 标志识别并剔除临时地址；
   Linux 上按 `mngtmpaddr`/`noprefixroute` 等标志与 `RFC 7217` 判定；
3. 或改用 RFC 7217 稳定隐私地址，并在注册记录里只发布它。

这条与 §6 的"未回答问题 2"是同一件事。

## 5. 实现中踩到的坑（务必保留，避免重犯）

这一节记录的是**真实调试过程**中定位到的问题。它们的共同特征是：现象都是
"AEAD 校验失败 / MAC check failed"，而根因各不相同。因此当握手失败时，
不要只看"密钥对不对"，要按下面的清单逐项排查。

### 5.1 Noise_XX 的 token 顺序与 nonce 延续（三处错误）

按噪声规范 §5.3 的 `WriteMessage` 规则：**先顺序处理消息的所有 token，最后才追加
一次负载**。由此推出的三条约束，本实现最初全部搞错：

| # | 规则 | 错误写法 | 正确写法 |
| --- | --- | --- | --- |
| 1 | `es` 的第一个字母指**发起方**的密钥类型 | 发起方用 `DH(e, re)` | 发起方 `DH(e, rs)`；响应方 `DH(s, re)`，且在**收到消息 3** 时才结算 |
| 2 | 负载用的是**最后一个 token 派生出的 k** | 把负载放在 `es`/`se` 之前 | `es`/`se` 的 `MixKey` 之后才加密负载 |
| 3 | 同一个 `k` 的 nonce **不因新消息而重置** | 消息 3 的 `s` 从 nonce 0 开始 | 响应方消息 2 已用掉 nonce 0，消息 3 的 `s` 用 nonce 1 |

补充一条容易忽略的：`CipherState` 在 `k` 为空时 `EncryptWithAd` **原样返回明文**
并只做 `MixHash`（XX 的消息 1），因此 `MixHash` 必须由 `HandshakeState` 负责，
不能让 `CipherState` 去持有握手哈希。

### 5.2 Ed25519 密钥不能直接当 X25519 用（最危险的一个）

* 现象：双方各自算出的 `DH(e_i, s_r)` 与 `DH(s_r, e_i)` **不相等**，
  但两边的代码都不报错，直到后面的 AEAD 才以 `MAC check failed` 暴露。
* 根因：Ed25519 的私钥是种子经 SHA-512 派生的**标量**，不是 X25519 标量；
  把它原样喂给 X25519 点乘，得到的是一把无关的标量。
* 修正：由同一份身份种子确定性派生 X25519 密钥对
  （`X25519 私钥 = clamp(BLAKE2s(seed || label))`），并在握手中用
  **设备绑定证明**把 Ed25519 设备公钥与 X25519 握手公钥绑定
  （否则 `authorize_peer` 会拿 DH 公钥去名单里查，永远查不到 —— 名单里存的是 Ed25519 公钥）。

### 5.3 pycryptodome 的两处编码陷阱

| 陷阱 | 表现 | 正确做法 |
| --- | --- | --- |
| Curve25519 的 `pointQ.x` 与 `export_key(format='raw')` **不是同一编码** | 用 raw 导出公钥、对端喂给 `EccXPoint`，DH 静默失败 | 统一用 `dh_public_bytes()`（`pointQ.x` 大端整数） |
| Ed25519 的 `int(key.d)` 是**派生标量**，不是种子 | 存 `d` 再重建会得到另一把密钥 | 持久化用 `key.seed`；重建用 `ECC.construct(curve='Ed25519', seed=...)` |

另有两处 API 事实：`ECC.import_key` **不接受** 32 字节裸 Ed25519 公钥（需补固定 SPKI
头 `302a300506032b6570032100`），也不接受裸种子；`EccXPoint(None, curve)` 是**无穷远点**
而不是基点，基点要取 `ECC._curves['Curve25519'].G`。

### 5.4 授权必须在握手之后单独确认

XX 的三条消息只完成"互相认证静态公钥"。响应方判定对端资格所需的最后一个输入
（发起方的静态公钥与绑定负载）在**消息 3** 才到达，而发起方在收到消息 2 后就已经
把消息 3 发出去了。因此：

* 不加确认帧时，被拒的发起方会认为 `connect()` **成功**（实测现象），
  直到后续请求失败或超时才发现；
* 修正：会话建立后的第一帧由响应方回 `ok` 或 `deny:<原因>`，
  发起方据此决定是否返回连接。

### 5.5 跨机联调的环境坑（与协议无关，但会浪费大量时间）

| 现象 | 根因 | 做法 |
| --- | --- | --- |
| `bash: $'\r': command not found` | 用 PowerShell 管道喂 bash 时行尾是 CRLF | 喂之前 `-replace "\`r\`n","\`n"` |
| `ssh` 卡满 120 秒超时，服务其实已启动 | `nohup ... &` 仍继承 ssh 的 stdout 管道 | 用 `systemd-run --unit=...` 起临时 unit |
| `ssh $alias "a" + "b"` | ssh 是原生命令，参数被拆开，远端收到孤立的 `+` | 先把整条命令拼进一个变量 |
| 控制台中文乱码导致断言假命中 | 代码页不是 UTF-8 | 断言用**退出码**，不用输出文本 |
| IPv6 地址直接拼进 `host:port` | 地址自带冒号，`rpartition(':')` 会切错 | 写成 `[2409:…]:port`，解析时去掉方括号 |
| "没有 IPv6"的错误结论 | `ssh host '... \' ...'` 引号嵌套失败，把报错当成了探测结果 | 探测类命令**必须看退出码**，别只看输出 |

最后一条值得单独强调：本次就因为一条引号写坏的 `ip -6 addr` 命令，得出了
"目标机没有全局 IPv6"的错误结论，并据此写进了文档。**探测结果与预期不符时，
先确认那条探测命令真的跑成功了。**

### 5.6 长驻节点的名单必须在每次建连时重读

* 现象：先起 `serve`，再在另一处执行 `roster add`，新成员连接时被判
  `对端设备 … 不在团体名单里，拒绝连接`。
* 根因：`Node` 只在构造时拿到一份名单快照，而它是长驻进程。名单是会变的
  （群主加人、改角色），快照会一直停在启动那一刻。
* 修正：`Node.current_roster()` 在**每条连接**上调用 `roster_loader` 重新读取名单；
  CLI 与插件分别传入"读 `roster.json`"与"读插件身份目录"的 loader。
  读盘失败时退回内存副本，不让一次 IO 错误导致全部连接被拒。
* 附带结论：这条修复让 `tools/ipv6-test.ps1` 的"先起节点、后加成员"顺序
  成了一个有效的回归用例。

### 5.7 CSS 级联废掉了 `hidden`（前端"一打开就弹添加成员"）

* 现象：打开插件，**三个弹窗同时铺满整屏**，DOM 里写在最后的"添加成员"盖在最上面，
  用户连"创建身份"都点不到。服务端返回完全正常（`identity: null`，全新区状态）。
* 根因：浏览器给 `[hidden]` 的 `display: none` 来自 **UA 样式表**，而
  `.gm-modal { display: flex }` 是作者样式。两者优先级相同（都是一个类/属性选择器），
  **作者样式胜出** —— 于是 `hidden` 属性写对了也照样显示。这类缺陷 Python 单测与
  静态检查都发现不了：属性确实存在，是级联把它废掉了。
* 修正：不跟 UA 样式博弈，改成属性选择器驱动默认态：

  ```css
  .gm-modal { display: none; }                    /* 默认态没有任何规则命中 */
  .gm-modal[data-open="true"] { display: flex; }  /* 显式打开 */
  ```

  比"再加一条 `.gm-modal[hidden] { display: none }`"更稳：默认不显示不依赖
  与 UA 的优先级关系，也不依赖 `<script>` 的加载位置。
* 教训：**前端"接上了"不等于"看得到"，也不等于"点得动"**。此前我对插件只做了
  后端 API 测试（18 例全过），前端一行没验 —— 而后端全对、界面全错是完全可能的。

### 5.8 状态载荷缺键，导致按钮"点了没反应"

* 现象：「创建团体」点击后毫无反馈。
* 根因：后端状态载荷里 `settings` 只给了 `port` 与 `bind`，**没有 `group_name`**，
  而前端读 `status.settings.group_name`。更糟的是当时的判断写成：

  ```js
  if (group !== (status.settings.group_name || '') || !window.confirm(...)) { return; }
  ```

  在 `group_name` 缺失时 `group` 是 `undefined`、右边是 `''`，`undefined !== ''` 恒真，
  于是走了 `window.confirm()` —— 而内嵌 WebView 里原生对话框可能被禁用，
  点击就完全没反应。
* 修正：①「创建团体」改成应用内弹窗（与其它动作一致，不再依赖原生对话框）；
  ② 状态载荷补齐前端会读的键，并**只给前端真正读的键**。
* 教训：桩测试容易掩盖这类问题 —— 我的用例对 `get_status` 回的是**手写的理想载荷**，
  键当然是齐的。因此又加了 `tests/test_group_mesh_shell_e2e.py`：起**真实 Shell 服务**、
  经导航点进插件 iframe，用真实后端返回值验证渲染与调用。

### 5.9 前端验证的三个层次（缺一层就会漏）

| 层次 | 用例 | 能抓到什么 | 抓不到什么 |
| --- | --- | --- | --- |
| 纯渲染 | `test_group_mesh_frontend_e2e.py`（桩 Bridge + 无头浏览器） | 弹窗可见性、按钮是否开弹窗/调后端、布局 | 真实鉴权、`Bridge` 的真实来源、`<plugin>__<method>` 前缀 |
| 真实壳 | `test_group_mesh_shell_e2e.py`（起服务 + 导航 + iframe） | 上面那三项，以及"插件在壳里到底能不能用" | 需要本机有浏览器（CI 上跳过） |
| 后端 | `test_group_mesh_plugin.py` | API 语义、契约（受保护路径）、共享根约束 | 界面 |

* 顺带澄清一个易踩的前提：**打开首页时壳会自己种下 HttpOnly 令牌 Cookie**
  （`file_server._attach_token_cookie`），因此 e2e 用例不需要手动准备令牌；
  反过来，若**直接**打开 `/plugins/<name>/frontend/index.html`，既拿不到这个 Cookie
  上下文，也拿不到壳注入的 `window.pywebview.api` 垫片，`Bridge` 会一直报
  "PyWebView API 不可用" —— 排查"插件一片空白"时先确认走的是壳的 URL。
  现在有三层用例覆盖，见 §5.9。先是 `tests/test_group_mesh_frontend_e2e.py`：用桩 Bridge 把
  `frontend/index.html` 真加载进无头浏览器，断言"弹窗默认不可见""全新安装时
  入口是创建身份而不是添加成员"以及三个弹窗的开关确实生效。
  已验证该用例在缺陷复现时会红（4 failed + 2 errors），不是空转。
* 顺带排查：`media-player` 用的是 `.mp-modal.active { display: flex }` 的写法，
  默认态同样没有规则命中，**不受此问题影响**；这类"默认 flex + 靠 hidden 关"
  的写法在本仓库只有 group-mesh 一处。

### 5.10 名单只做了"第一次加入"，没做"分发更新"（成员停在旧名单）

* 现象：群主在 A 机把自己与 B 机都加进名单（v2），B 机界面里却始终只有 v1、
  看不到自己、也连不上任何人；A 机看到的成员表与 B 机不一致。
* 排查结论（用真实数据核对）：**不是"进不了名单"，是名单没送到**。
  A 机 roster v2、B 机 roster v1，且 A 的 `prev` 正好等于 B 的名单哈希 ——
  也就是 B 只要拿到 v2 就能接上，规则链本身没问题。
* 根因：名单是**带外分发**的（§5.2 规则 6 的"信任锚"），而实现里只有"首次加入"
  这一个入口。群主 `roster add` 之后签发的新名单没有任何机制到达成员端，
  于是成员永远停在旧名单上：

  | | 名单 | 对 `flotiarenorserver` 的判定 |
  | --- | --- | --- |
  | Windows（群主） | v2 | 在名单里 → 接受它连接 |
  | Linux（成员） | v1 | 不在名单里 → **拒绝连接**（看到的是"进不了名单"） |

* 修正：
  1. 后端把"加入"与"更新"合并为同一路径（验证规则本来就是同一套：无名单走规则 6，
     有名单走规则 1/2 的直接后继检查），并在返回值里区分 `updated` 与首次加入；
  2. 界面上那个入口改名 **「加入 / 更新团体」**，弹窗里写明"群主每次加人后都要把新
     邀请串发给你"，避免用户以为只有第一次才用得到；
  3. 给出比本机更旧的邀请串时，错误信息带版本号（"本机已是 v2，拿到的是 v1"），
     否则用户只会看到一句"版本未前进"，不知道该怎么办。
* 验证：`tests/test_group_mesh_plugin.py::RosterDistributionTest` 覆盖
  v1→v2 更新成功、旧邀请串被拒且提示带版本、**跳版（v1→v3）被规则 2 拒绝**。
  另外用两台机器的**真实插件身份**做了端到端复核：Linux 名单 v1→v2 后，
  Windows 连入成功（Noise 握手 + 名单授权），400 KB 文件传输一致，越权写入被拒。
* 遗留：目前仍**只有手动分发**（把邀请串发给每个人）。设计文档 §7.3 的注册表可以
  顺带承载名单扩散，但那需要一个"群主之外的中转不能篡改内容"的设计 ——
  名单本身是有签名的，因此技术上可行，留待 P2。
