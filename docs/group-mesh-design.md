# 团体组网插件（group-mesh）设计文档

> 版本：v0.1（首版设计：需求与协议骨架定稿）
> 目标形态：**核心插件**（供消费型插件依赖）+ 壳侧配套改造
> 状态：**设计阶段**，尚未实现
> 关联文档：`docs/plugin-guide.md`、`docs/core-direction.md`、`docs/ci-and-release.md`

---

## 1. 定位

### 1.1 目标

为若干互相信任的使用者提供一套无中心的组网能力，使各自设备在公网 IPv6 上完成下列事项：

1. 互相发现并完成身份认证；
2. 按授权共享文件，允许各成员把自己的设备接入团体；
3. 为老游戏的局域网联机提供二层虚拟局域网；
4. 为文字与语音提供传输通道；
5. 在有成员提供高带宽节点时，允许房间切换到中心化转发。

### 1.2 与仓库现有插件的关系

本插件是**核心插件**，自身不直接面向最终用途，只提供身份、团体、注册、发现与传输。文件传输、游戏联机、文字与语音作为 Companion 插件，通过 `manifest.dependencies: ["group-mesh"]` 声明依赖，经 `PluginBase.get_dependency('group-mesh')`（`shell/backend/plugin_base.py:128`）与 `Bridge.callPlugin` 使用其能力。

此结构与 `docs/core-direction.md` §1 定义的 Companion 插件形态一致。

### 1.3 非目标

| 项 | 说明 |
| --- | --- |
| 无公网 IPv6 的使用者 | 不提供 IPv4 NAT 穿透或公共中继兜底 |
| Android 端完整节点 | 首版不实现，仅预留轻客户端角色（见 §11.2） |
| 自动更新 | 不做后台轮询与静默替换，更新由用户从 GitHub Release 手动下载 |
| 集中式账号服务 | 不设中心服务器；团体之间默认完全隔离 |
| IPX 老游戏 | 现代 Windows 已移除 IPX 协议栈，不纳入范围 |

## 2. 术语

| 术语 | 标识 | 含义 |
| --- | --- | --- |
| 主体 | principal | 一个人。持有长期密钥对，可以拥有多台设备 |
| 设备 | device | 一台机器。持有自己的密钥对，归属于某个主体 |
| 团体 | group | 身份与授权的边界。由一名群主与一个成员集合构成 |
| 群主 | owner | 团体的创建者。唯一可签发名单、任命管理员、解散团体的主体 |
| 管理员 | admin | 由群主任命的主体。可增删普通成员，不涉及数据 |
| 成员 | member | 团体成员。无成员管理权，按共享项 ACL 访问数据 |
| 共享节点 | share node | 已把自身地址注册进团体、对外提供共享项的节点 |
| 共享项 | share | 某设备上的一个目录及其 ACL。权限由该设备的属主主体签发 |
| 房间 | room | 一次具体活动（联机、语音）的临时集合。独立于团体 |
| 注册 | registration | 共享节点发布的自身端点与共享清单记录 |
| 团体名单 | roster | 群主或管理员签名的成员与角色清单 |

## 3. 形态与角色

### 3.1 无中心

系统内不存在必须常驻的服务器。任何设备都可以：

- 创建一个团体并成为其群主；
- 把自己的地址注册为共享节点，开机即可被访问，关机即退出；
- 在房间中承担中继或房间主机。

「共享区」不是集中存储，而是各成员主动共享出来的内容的聚合视图。

### 3.2 角色

| 角色 | 权限 |
| --- | --- |
| 群主 | 增删成员、任命与撤销管理员、签发团体名单、解散团体、转移群主 |
| 管理员 | 增删普通成员 |
| 成员 | 无成员管理权；按各共享项的 ACL 读写删 |

管理员与群主的差异体现在名单签发的限制上，见 §5.2。

### 3.3 两个正交的权威面

| 权威面 | 持有者 | 作用范围 | 载体 |
| --- | --- | --- | --- |
| 团体成员权威 | 群主与管理员 | 谁的名单里有谁 | 团体名单 |
| 设备资源权威 | 每台设备所属的主体 | 该主体设备上的共享项与 ACL | 共享项声明 |

不存在第三个权威面：**群主与管理员对成员设备上的数据没有任何特权**，访问他人共享内容时与普通成员走同一套 ACL。资源属主按**主体**判定，不按设备判定，因此同一主体的手机访问自己主力机上的共享项时按属主处理。

### 3.4 平面划分

| 平面 | 传输 | 用途 |
| --- | --- | --- |
| 应用面 | 自有协议，直接使用 IPv6 | 身份、注册、发现、共享、文件传输、语音信令与语音 |
| 游戏面 | SoftEther 的二层隧道 | 老游戏的虚拟局域网 |

两个平面共用同一套身份、名单与注册表，传输层各自独立。

## 4. 身份与密钥

### 4.1 主体与设备分离

一个主体可以拥有多台设备；权限绑定在主体上，因此新增设备不需要重新配置权限。设备私钥不导出，由操作系统提供的密钥存储保存（Windows 为 DPAPI，Android 为 Keystore）。

### 4.2 设备注册

1. 新设备生成密钥对；
2. 通过已有设备授权（局域网配对或二维码）由该主体确认；
3. 该主体的已有设备签发一份绑定 `principal_id + device_pubkey` 的设备凭据；
4. 凭据进入团体名单并分发。

### 4.3 身份统一

同一个设备密钥同时用于应用面握手与共享节点注册，不维护第二套账号。

### 4.4 传输层

应用面采用**名单 + Noise 握手**，模式取 `Noise_XX`：

- 握手使用 Noise 框架的现成实现，不自行设计密码学组合；
- 模式取 `XX`：两端均持有名单，不需要预先知道对方的静态密钥，握手过程中双方互相认证并交换静态公钥；
- 默认套件为 `25519 / ChaCha20-Poly1305 / BLAKE2s`，套件可通过协商替换，字段见 §4.5；
- 数据使用标准 AEAD 加密，密钥由 HKDF 从握手结果派生；
- 每条会话使用临时密钥，具备前向安全。

选择理由：数据层两端都由本项目实现，X.509 的互操作价值在此不成立；名单同时承担认证与撤销两项职责，状态最少，且与 §5.4 的宽限策略契合。

### 4.5 协议协商字段

握手开始时双方各发一条明文消息：

```json
{
  "proto": 1,
  "suites": ["noise-XX-25519-chacha20poly1305-blake2s"],
  "features": ["roster-v1", "room-relay", "share-write"]
}
```

| 字段 | 含义 | 变更语义 |
| --- | --- | --- |
| `proto` | 协议主版本 | 不兼容变更时递增；双方主版本不一致则断开并提示升级 |
| `suites` | 支持的加密套件，按偏好排序 | 取交集后选优先级最高者；无交集则断开 |
| `features` | 可选能力开关 | 未声明即按旧行为处理 |

两条实现约束：

1. 协商结果必须并入被认证的握手转录（Noise 的 prologue），否则存在降级攻击面；
2. 该消息在认证之前处理，解析必须做长度与取值边界检查。

## 5. 团体名单

### 5.1 结构

```json
{
  "group":   "<团体标识>",
  "version": 12,
  "prev":    "<前一份名单的哈希>",
  "expires": 1767225600,
  "owner":   "<群主主体公钥>",
  "admins":  ["<主体公钥>"],
  "members": [
    {"name": "alice", "pubkey": "<主体公钥>", "devices": ["<设备公钥>"]}
  ],
  "sig": "<签名>"
}
```

### 5.2 验证规则

验证相对本地当前持有的名单 `cur` 执行：

| # | 规则 | 作用 |
| --- | --- | --- |
| 1 | `new.version > cur.version` | 防回滚 |
| 2 | `new.prev == hash(cur)` | 只接受直接后继 |
| 3 | 签名者属于 `{cur.owner} ∪ cur.admins` | 只有群主与管理员可签发 |
| 4 | 签名者为 `cur.owner` 时无附加限制 | 群主全权，含转移群主与变更管理员集合 |
| 5 | 签名者为管理员时，要求 `new.owner == cur.owner` 且 `set(new.admins) == set(cur.admins)` | 管理员只能增删普通成员，不能改群主、不能改管理员集合、不能自我提权 |
| 6 | 本地名单为空时，直接信任带外分发的创始名单 | 信任锚起点 |

由规则 5 得出：任命与撤销管理员只有群主可做；群主转移属于规则 4 的范围，是群主密钥失效前唯一的自救手段。

### 5.3 并发签名与冲突

规则 2 保证一份名单只有一个直接后继。两名管理员同时签发不同后继时，二者 `prev` 与 `version` 相同。处理方式：**同版本、同 `prev` 时按名单哈希的字典序取较小者**。该规则是确定性的，各节点无需通信即可收敛；被丢弃的一份需要重新签发。

### 5.4 宽限策略

**软件不做版本强制。** 具体为：

- `expires` 为**提示字段**，到点不阻断通信；
- 版本号仍单调递增并写入名单，但节点不因对方名单较旧而拒绝连接；
- 界面提示「你的名单已过期 N 天 / 与对方名单不一致」，由团体自行协调。

需要写明的后果：**移除成员的有效窗口没有上界**。被移除者与已更新名单的节点无法握手，但与尚未更新的节点之间仍可通信，直到后者更新。该窗口由团体协调解决，软件不额外施加机制。

### 5.5 解散

解散是一条独立于名单的通告记录：

- 签名者必须是当前名单中的 `owner`，管理员签发的通告无效；
- 通告携带高于当前名单的版本号；
- 成员收到后停止使用该团体，**保留本地数据，不删除**；
- 无中心系统无法技术强制解散，该通告的实际效果是「有共识的终止」；已分发到成员设备上的数据无法回收。

### 5.6 群主密钥边界

群主密钥丢失等于该团体永久无法再管理（不能加人、不能删人、不能解散）。无中心系统没有恢复机制，唯一的缓解手段是群主在密钥仍有效时主动签发包含新 `owner` 公钥的名单完成转移。该限制需要写进使用说明。

## 6. 共享项与权限

### 6.1 结构

```json
{
  "node":     "<设备公钥>",
  "owner":    "<属主主体公钥>",
  "share_id": "<该设备内的共享标识>",
  "path":     "<本机目录>",
  "seq":      3,
  "acl": {
    "read":   "group",
    "write":  ["<主体公钥>"],
    "delete": "owner"
  },
  "sig": "<设备私钥签名>"
}
```

`read` / `write` / `delete` 三项取值均为 `"owner"`、`"group"` 或主体公钥数组。

### 6.2 写权限两档

| 档位 | `write` | `delete` |
| --- | --- | --- |
| 仅上传 | 授予对象 | 仅属主 |
| 可增删 | 授予对象 | 授予对象 |

**删除权完全由 ACL 决定，不由归属推断。** 因此不记录 `created_by` 用于授权判定；该元数据仅用于界面展示「这是谁上传的」。

由此产生的行为：在「仅上传」档位下，上传者不能撤回自己上传的文件（含误传），需由属主删除。

### 6.3 判定位置

判定在**属主设备**上执行。客户端隐藏按钮不构成授权；判定依据是发起方主体的公钥，该公钥来自握手，不接受请求参数中的自称身份。

### 6.4 审计与回收站

- 属主设备记录谁在何时写入、删除了什么；
- 删除不做物理删除，分两段处理：

| 阶段 | 行为 | 恢复方式 |
| --- | --- | --- |
| 一 | 移入该共享项的应用级回收站，默认保留 30 天 | 属主在界面中恢复或手动清空 |
| 二 | 30 天后移交操作系统回收站 | 用系统文件管理器恢复 |

第二阶段的平台约束：

| 平台 | 实现 | 约束 |
| --- | --- | --- |
| Windows | Shell 的 `SHFileOperation`（`FOF_ALLOWUNDO`） | 需要可用的 Shell 会话；作为服务或计划任务运行时不可用 |
| Linux | freedesktop.org 回收站规范 | 回收站必须与被删文件位于同一挂载点，跨文件系统时需要复制或直接失败；无桌面环境时依赖具体实现 |
| 网络挂载 | 由挂载协议决定 | SMB 是否有回收站取决于服务端，NFS 没有 |

该功能需要一个新增的第三方依赖（如 `send2trash`），按仓库约定需写入 `requirements.txt`，并把模块名列进 `docs/Releases/spec_common.py` 的 `HIDDEN_IMPORTS`。

移交系统回收站后空间在属主清空回收站之前不会释放，因此共享项的容量统计需要把应用级回收站计入。

### 6.5 安全边界

可写共享是数据投放面：被授予写权限的主体可以在属主目录内创建任意文件。必须实现：

- 严格路径校验，禁止越界与符号链接逃逸；
- 按共享项的容量上限（授予写权限等于允许对方占用磁盘）；
- 共享目录与程序目录、配置目录分离；
- 不提供远程重命名与移动。

## 7. 注册与发现

### 7.1 注册记录

```json
{
  "device":  "<设备公钥>",
  "seq":     7,
  "endpoints": [["240e:xxxx::1", 18443]],
  "shares":  ["<共享标识>"],
  "ts":      1767225600,
  "sig":     "<设备私钥签名>"
}
```

### 7.2 与名单解耦

| | 签名者 | 变更频率 | 内容 |
| --- | --- | --- | --- |
| 团体名单 | 群主或管理员 | 低频（成员增删） | 主体、角色、设备公钥 |
| 注册记录 | 设备自己 | 高频（开关机、地址变化） | 设备公钥、当前端点、共享清单、序号 |

注册是**成员自助**行为，不需要管理员参与，因此成员的开关机不影响团体管理。

### 7.3 同步方式

注册记录是小数据集：按 200 台设备估算，约 20～40 KB。因此**不使用 DHT**：

- 任一在线共享节点都能提供完整快照；
- 新上线设备拉取一次快照，之后按 `seq` 比对做增量同步；
- 记录带设备自身签名，中继方无法伪造内容。

### 7.4 地址变化与稳定地址

- 监听套接字与注册记录中的端点必须使用**稳定地址**（EUI-64 或 RFC 7217 stable-privacy），不使用 Windows 默认启用的 RFC 4941 临时地址，后者会轮换；
- 定期比对本机全球单播地址集合，变化则递增 `seq` 并重新发布；
- Windows 防火墙默认阻止入站，需要为监听端口添加规则（需管理员权限，一次性）。

### 7.5 容量核算

| 对象 | 规模估算 | 结论 |
| --- | --- | --- |
| 成员记录 | 50 人约 4 KB | 无压力 |
| 设备记录 | 200 台约 20 KB | 无压力 |
| 名单全量 JSON | 约 25 KB | 无压力 |
| 一次成员变更的全量分发 | 25 KB × 200 节点约 5 MB | 可忽略 |
| 全互联连接 | 200 台设备为 19900 对 | **不可行**，因此以星形为主，成员间直连按需建立 |

## 8. 房间

### 8.1 房间对象

```json
{
  "room":    "<房间标识>",
  "group":   "<所属团体>",
  "owner":   "<房主主体公钥>",
  "mode":    "mesh",
  "relays":  [{"device": "<设备公钥>", "endpoint": ["240e:xxxx::1", 18443]}],
  "members": ["<主体公钥>"],
  "expires": 1767225600,
  "sig":     "<房主签名>"
}
```

房间是一次具体活动的集合，独立于团体：团体是身份与授权边界，房间是联机或语音的临时 L2 域，拥有自己的虚拟 IPv4 网段。

### 8.2 模式

| 模式 | 拓扑 | 适用 |
| --- | --- | --- |
| `mesh` | 成员之间直连 | 语音建议 6 人以内；游戏 10 人以内 |
| `relay` | 经由一个或多个中继节点转发 | 人数超过上述范围，或直连失败时 |

中继节点可以由任一成员承担，包括在机房租用高带宽机器的成员。

### 8.3 语音

- 采用 WebRTC + Opus；
- 网状模式每人上行 = (N−1) × 约 40 kbps：5 人约 160 kbps，10 人约 360 kbps，50 人约 1.96 Mbps；
- 移动网络上行通常为 1～5 Mbps，因此人数较多时需要中继；
- 中继模式下每人只发一路给中继，中继上行约 N × 40 kbps（50 人约 2 Mbps）；
- **不设硬上限**；界面按当前模式标出可承载范围，并在超过 6 人时提示可以切换中继模式。该提示仅为建议，不阻断加入。

### 8.4 游戏

- 二层虚拟局域网中每条广播与组播帧必须复制给房间内其他每个节点，复制量由本项目承担，与游戏自身的服务端负载无关；
- 网状模式下发送方复制 N−1 份；改为星形中继后为发送方发 1 份、中继复制 N−1 份，上行压力从各节点集中到中继；
- 10 人房间每条广播复制 9 份，为实际支撑目标；**不设硬上限**；
- 整个团体不得置于同一 L2 广播域，房间必须独立划分。

### 8.5 知情同意

加入房间即接受房间声明（含模式与中继），不需要投票机制。两点必须如实标注：

- 中继可见通信元数据（谁与谁通信、流量大小）；
- 语音中继需要解密音频，因此**可见内容**；需要端到端加密的语音只能使用网状模式。

### 9.2 外部依赖的编排方式

参照 `netease-music` 的既有范式（`plugins/netease-music/backend/netease_music_api.py`）：外部程序由用户安装，插件负责定位、探测与调用。

| 项 | 设计 |
| --- | --- |
| 定位 | 优先取设置项中的用户指定目录（`settings_schema` 的 `directory` 类型，由 Shell 的 `FolderPicker` 渲染），其次探测系统 PATH |
| 探测 | 调用 `vpncmd` 获取版本；状态区显示「未安装 / 已安装 版本 X」 |

## 10. 传输与内容寻址

### 10.1 分块与寻址

成员之间的文件传输使用内容寻址的分块协议：文件切分为固定大小的块，每块以哈希标识，接收方可从任意持有者获取任意块。该设计复用 §7 的注册表作为来源目录。

### 10.2 做种

任何成员可以把已获取的内容保留并继续提供。这是可选项，用于实现「只要有一台机器没关机，资源仍可访问」。默认行为是内容仅由属主设备提供，属主离线即不可访问。

### 10.3 与 BitTorrent 的差异

不集成完整 BitTorrent：peer 发现已由 §7 提供，tracker 与 DHT 属于重复建设；引入 `libtorrent` 还会带来打包体积与 `HIDDEN_IMPORTS` 的额外成本。

## 11. 客户端形态

### 11.1 完整节点

Windows 与 Linux 上运行完整的 OmniBox 实例，本身即「本地网关 + 节点」，不需要额外组件。

### 11.2 轻客户端（Android，预留）

| 角色 | 能力 | 平台 |
| --- | --- | --- |
| 完整节点 | 持有名单、可作为共享节点、可作房间主机与中继 | Windows、Linux |
| 轻客户端 | 只有身份密钥；可读取共享内容、传输文件、参与语音 | Android（首版不实现） |

首版只需在协议中预留该角色：角色字段加能力声明，不预留具体接口。协议不假设每个参与者都承担存储与转发。

### 11.3 本地网关

轻客户端的形态是在客户端内部运行一个仅监听 `127.0.0.1` 的 HTTP 服务：

```
[WebView] --http://127.0.0.1:port--> [本地网关] --团体加密通道--> [共享节点]
```

WebView 加载 `http://127.0.0.1:<端口>/`，页面内的 `/api`、`/file`、`/thumbs` 请求由网关经加密通道转发。三点作用：

1. `127.0.0.0/8` 属于 potentially trustworthy origin，WebView 无需证书即为安全上下文，麦克风可用；
2. 前缀变化、证书重签、`iPAddress` 匹配均不涉及；
3. 不存在第二套账号。

代价是网关需要正确转发 Range 请求，否则媒体播放会退化为整文件下载；Android 的明文流量策略需按目标版本确认。

## 12. 壳侧配套改造

本插件依赖下列壳侧能力，均属新增，插件层无法单独完成。

| # | 项 | 现状 | 需要新增 |
| --- | --- | --- | --- |
| 1 | 调用者身份 | `/api/<method>` 只校验单一令牌（`shell/backend/auth.py`，88 行，无账号与按成员凭据） | 凭据到主体的映射；每请求确立主体上下文 |
| 2 | 插件读取主体 | 插件方法无主体入参，且请求参数可被伪造 | Shell 以受信方式注入（`before_request` 设置 `ContextVar`），`PluginBase` 提供读取方法 |
| 3 | 数据路由授权 | `/file`、`/thumbs` 只做路径安全校验 | 主体级授权检查点 |
| 4 | 文件根 | `get_file_roots()` 返回本机根目录列表 | 支持远端共享来源 |
| 5 | 设置写入 | `system_settings_save` 无权限检查 | 限群主与管理员 |
| 6 | 插件兼容性 | `minShellVersion` 仅由 `tools/check_plugins.py` 读取，运行时既不告警也不拒绝加载（`docs/plugin-guide.md:80`、`:94`） | 加载时运行时校验，不满足则拒绝加载并给出原因 |

第 2 项的实现约束：插件自起的后台线程不继承请求上下文，涉及主体的后台任务必须显式携带主体信息。
