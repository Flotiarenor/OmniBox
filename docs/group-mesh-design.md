## 1. 定位

### 1.1 目标

为若干互相信任的使用者提供一套无中心的组网能力，使各自设备在公网 IPv6 上完成下列事项：

1. 互相发现并完成身份认证；
2. 按授权共享文件，允许各成员把自己的设备接入团体；
3. 为上层插件提供统一的加密传输通道（谁在用、用来传什么由 Companion 插件决定）。

> **现状**：[部分]。第 1 项已实现；第 2 项已实现**读取与上传**；第 3 项已有
> offset/length 分块传输（§10 的内容寻址尚未实现），排期见 §16。
>
> 老游戏联机（二层虚拟局域网）与语音**不属于本插件的目标**，它们由未来的
> Companion 子插件承担、复用本插件的身份与通道，设计草案见
> [group-mesh 的 Companion 子插件](./group-mesh-companions.md)。

### 1.2 与仓库现有插件的关系

本插件是**核心插件**，自身不直接面向最终用途，只提供身份、团体、注册、发现与传输。文件传输、游戏联机、文字与语音作为 Companion 插件，通过 `manifest.dependencies: ["group-mesh"]` 声明依赖，经 `PluginBase.get_dependency('group-mesh')`（`shell/backend/plugin_base.py`）与 `Bridge.callPlugin` 使用其能力。

此结构与 `docs/core-direction.md` §1 定义的 Companion 插件形态一致。

协议内核放在 `shell/groupmesh/`（与 `shell/backend`、`shell/frontend` 并列的壳层包），
而不是某个插件的私有目录：它要被多个 Companion 插件复用，且必须能脱离 GUI 独立运行
（不 import Flask / pywebview）。分层与理由详见实现路径文档 §2。

> **现状**：[已实现]。内核在 `shell/groupmesh/`，插件在 `plugins/group-mesh/`，
> 已列入 `docs/Releases/spec_common.py` 的 `HIDDEN_IMPORTS`（打包不丢内核）。
> `manifest.json` 的 `dependencies` 为空数组，是"核心插件"当前的表达方式；
> manifest 尚无 `kind` 字段可用于声明核心插件。

### 1.3 非目标

| 项 | 说明 |
| --- | --- |
| 无公网 IPv6 的使用者 | 不提供 IPv4 NAT 穿透或公共中继兜底 |
| Android 端完整节点 | 首版不实现，仅预留轻客户端角色（见 §11.2） |
| 自动更新 | 不做后台轮询与静默替换，更新由用户从 GitHub Release 手动下载 |
| 集中式账号服务 | 不设中心服务器；团体之间默认完全隔离 |
| IPX 老游戏 | 现代 Windows 已移除 IPX 协议栈，不纳入范围 |

## 2. 术语

| 术语 | 标识 | 含义 |
| --- | --- | --- |
| 主体 | principal | 一个人。持有长期密钥对，可以拥有多台设备 |
| 设备 | device | 一台机器。持有自己的密钥对，归属于某个主体 |
| 团体 | group | 身份与授权的边界。由一名群主与一个成员集合构成 |
| 群主 | owner | 团体的创建者。唯一可签发名单、任命管理员、解散团体的主体 |
| 管理员 | admin | 由群主任命的主体。可增删普通成员，不涉及数据 |
| 成员 | member | 团体成员。无成员管理权，按共享项 ACL 访问数据 |
| 共享节点 | share node | 已把自身地址注册进团体、对外提供共享项的节点 |
| 共享项 | share | 某设备上的一个目录及其 ACL。权限由该设备的属主主体签发 |
| 房间 | room | 一次具体活动（联机、语音）的临时集合。独立于团体 |
| 注册 | registration | 共享节点发布的自身端点与共享清单记录 |
| 团体名单 | roster | 群主或管理员签名的成员与角色清单 |

## 3. 形态与角色

### 3.1 无中心

系统内不存在必须常驻的服务器。任何设备都可以：

- 创建一个团体并成为其群主；
- 把自己的地址注册为共享节点，开机即可被访问，关机即退出；
- 在房间中承担中继或房间主机。

「共享区」不是集中存储，而是各成员主动共享出来的内容的聚合视图。

### 3.2 角色

| 角色 | 权限 |
| --- | --- |
| 群主 | 增删成员、任命与撤销管理员、签发团体名单、解散团体、转移群主 |
| 管理员 | 增删普通成员 |
| 成员 | 无成员管理权；按各共享项的 ACL 读、写 |

管理员与群主的差异体现在名单签发的限制上，见 §5.2。

> **现状**：[已实现]。角色由名单推导（`roster.py` 的 `role_of()`），
> 规则 4/5 在签发时强制；但**转移群主与任免管理员目前只有 CLI**（§5.6）。

### 3.3 两个正交的权威面

| 权威面 | 持有者 | 作用范围 | 载体 |
| --- | --- | --- | --- |
| 团体成员权威 | 群主与管理员 | 谁的名单里有谁 | 团体名单 |
| 设备资源权威 | 每台设备所属的主体 | 该主体设备上的共享项与 ACL | 共享项声明 |

不存在第三个权威面：**群主与管理员对成员设备上的数据没有任何特权**，访问他人共享内容时与普通成员走同一套 ACL。资源属主按**主体**判定，不按设备判定，因此同一主体的手机访问自己主力机上的共享项时按属主处理。

### 3.4 平面划分

本插件只做**应用面**：自有协议、直接使用 IPv6，承载身份、注册、发现、共享与文件传输。

老游戏的二层虚拟局域网是**游戏面**，由未来的 Companion 子插件用 SoftEther 隧道实现；
两个平面共用同一套身份、名单与注册表，传输层各自独立（草案见
[Companion 子插件](./group-mesh-companions.md)）。

> **现状**：[部分]。应用面已实现身份、注册、发现、共享与文件传输（语音信令不在本插件
> 范围内）；游戏面由子插件负责。

## 4. 身份与密钥

### 4.1 主体与设备分离

一个主体可以拥有多台设备；权限绑定在主体上，因此新增设备不需要重新配置权限。设备私钥不导出，由操作系统提供的密钥存储保存（Windows 为 DPAPI，Android 为 Keystore）。

> **现状**：[部分]。
>
> - 主体/设备分离、多设备的数据结构已经实现（`identity.py` 的 `Identity`，目录布局
>   `identity/principal.json` + `identity/devices/<id>.json`）。
> - **私钥当前是明文落盘的**（base64 JSON），只有目录 0700 / 文件 0600 保护，
>   Windows 上 `chmod` 语义受限、异常被吞掉。唯一的补偿是身份目录申报为受保护路径
>   （`plugins/group-mesh/backend/main.py` 的 `get_protected_paths()`），
>   `/file`、`/files`、`/thumbs` 对它一律 403。
> - 收敛路径：Windows 走 DPAPI（`CryptProtectData`），Linux 走 keyring 或口令派生的
>   KEK。**这是当前最高危的一处偏离，属 §16 的 P1。**
> - 多设备入口缺失：`identity.py` 的 `add_device()` 已实现但**无任何调用方**
>   （CLI 与插件都没有暴露），见 §16 P2。

### 4.2 设备注册

1. 新设备生成密钥对；
2. 通过已有设备授权（局域网配对或二维码）由该主体确认；
3. 该主体的已有设备签发一份绑定 `principal_id + device_pubkey` 的设备凭据；
4. 凭据进入团体名单并分发。

> **现状**：[部分]。
>
> | 步骤 | 状态 | 说明 |
> | --- | --- | --- |
> | 1 生成密钥对 | [已实现] | `identity.py` 的 `Device.create()` |
> | 2 已有设备授权（配对/二维码） | [未实现] | 无任何配对通道 |
> | 3 签发设备凭据 | [部分] | 凭据存在且可验签，但由**本机主体私钥自签**，不是"已有设备签发" |
> | 4 凭据进名单并分发 | [未实现] | 名单条目只有 `name` / `principal_key` / `device_keys`，不含凭据；握手只查设备公钥是否在册，**从不校验凭据** |
>
> 因此第 2–4 步是**待设计**而不是待实现：在没有跨设备授权通道之前，
> 凭据字段只是本机自签的完整性标记。

### 4.3 身份统一

同一份身份材料同时用于应用面握手与共享节点注册，不维护第二套账号。

**修订（v0.2）**：实现上不是"同一把密钥"，而是**同一份身份种子派生两把用途分离的密钥**：

- Ed25519 密钥对负责签名（名单、共享项声明、注册记录、设备凭据）；
- X25519 密钥对由同一份种子确定性派生（`crypto_prims.py` 的 `dh_keypair_from_sign_seed()`），负责 Noise 握手的静态密钥。

这不是实现偏好，而是必要约束：**Ed25519 私钥是种子经 SHA-512 派生的标量，不是合法的
X25519 标量**，直接当 DH 用会让双方算出不同的共享密钥且都不报错，直到 AEAD 才以
`MAC check failed` 暴露（详见实现路径文档 §5.2）。为了让"名单里存的是 Ed25519 公钥"
与"握手拿到的是 X25519 公钥"能对上，握手时附一份**设备绑定证明**把两者绑在一起
（`identity.py` 的 `encode_binding_payload()` / `make_binding()`）。

从"账号数量"的角度仍然只有一套身份材料，但不满足原措辞的"同一把密钥"。

> **现状**：[已实现]。

### 4.4 传输层

应用面采用**名单 + Noise 握手**，模式取 `Noise_XX`：

- 握手使用 Noise 框架的现成实现，不自行设计密码学组合；
- 模式取 `XX`：两端均持有名单，不需要预先知道对方的静态密钥，握手过程中双方互相认证并交换静态公钥；
- 默认套件为 `25519 / ChaCha20-Poly1305 / BLAKE2s`，套件可通过协商替换，字段见 §4.5；
- 数据使用标准 AEAD 加密，密钥由 HKDF 从握手结果派生；
- 每条会话使用临时密钥，具备前向安全；
- **长连接必须轮换传输密钥（新增，v0.2）**：按消息数或字节数触发 Noise §11.3 的 `Rekey()`，
  或限制单连接时长后强制重握手。

> **现状**：[部分]，三处需要如实记录：
>
> 1. **状态机是自写的**。只复用了已审计的密码学原语（pycryptodome），
>    按 Noise 规范 §5.3/§7.5 自己实现握手与传输态（`noise.py`）。
>    安全性来自"原语正确 + 状态机照规范写"，**不是**来自长期审查过的协议实现 ——
>    本次实现中 XX 的 token 顺序与 nonce 延续规则确实错了三次（实现路径文档 §5.1）。
> 2. **没有官方测试向量**。现有用例只验"两端能互通"（`tests/test_group_mesh_mvp.py` 的
>    `NoiseXXTest`），仓库内没有任何 Noise 规范向量文件。
> 3. **DH 公钥编码不是 RFC 7748**。`crypto_prims.py` 的 `dh_public_bytes()` 用的是
>    pycryptodome 的 `pointQ.x` 大端整数，与外部实现不互通。这一点决定了收敛顺序：
>    **必须先改公钥编码，再换 vetted 实现，官方向量才可能跑得通**；否则"换成
>    `snow`/`noiseprotocol`"这一步会以失败告终。
> 4. **密钥轮换未实现**：唯一的上限是 nonce 计数器耗尽（`noise.py` 直接报错终止，
>    不是 rekey）。单条超长连接泄露一把传输密钥，该连接内全部内容可解。

### 4.5 协议协商字段

握手开始时双方各发一条明文消息：

```json
{
  "proto": 1,
  "suites": ["noise-XX-25519-chacha20poly1305-blake2s"],
  "features": ["roster-v1", "registration-v1", "share-read", "share-range"]
}
```

| 字段 | 含义 | 变更语义 |
| --- | --- | --- |
| `proto` | 协议主版本 | 不兼容变更时递增；双方主版本不一致则断开并提示升级 |
| `suites` | 支持的加密套件，按偏好排序 | 取交集后选优先级最高者；无交集则断开 |
| `features` | 可选能力开关 | 未声明即按旧行为处理 |

**修订（v0.2）**：`features` 的实际取值以上表为准。原示例中的 `room-relay` 与
`share-write` 尚未实现（前者随 §8，后者随 §6.2 的写权限入口），实现里新增了
`registration-v1`、`share-read`、`share-range`。

两条实现约束：

1. 协商结果必须并入被认证的握手转录（Noise 的 prologue），否则存在降级攻击面；
2. 该消息在认证之前处理，解析必须做长度与取值边界检查。

> **现状**：[已实现]（`transport.py` 的 `negotiate()`、prologue 见 `noise.py`）。
> 已知局限：`KNOWN_SUITES` 目前只有一套套件，"可协商替换"尚无第二个套件可切。

## 5. 团体名单

### 5.1 结构

```json
{
  "group":   "<团体标识>",
  "version": 12,
  "prev":    "<前一份名单的哈希>",
  "expires": 1767225600,
  "owner":   "<群主主体公钥>",
  "admins":  ["<主体公钥>"],
  "members": [
    {"name": "alice", "pubkey": "<主体公钥>", "devices": ["<设备公钥>"]}
  ],
  "sig": "<签名>"
}
```

> **现状**：[已实现]（`roster.py` 的 `Roster`，字段集合与上表一致）。

### 5.2 验证规则

验证相对本地当前持有的名单 `cur` 执行：

| # | 规则 | 作用 |
| --- | --- | --- |
| 1 | `new.version > cur.version` | 防回滚 |
| 2 | `new.prev == hash(cur)` | 只接受直接后继 |
| 3 | 签名者属于 `{cur.owner} ∪ cur.admins` | 只有群主与管理员可签发 |
| 4 | 签名者为 `cur.owner` 时无附加限制 | 群主全权，含转移群主与变更管理员集合 |
| 5 | 签名者为管理员时，要求 `new.owner == cur.owner` 且 `set(new.admins) == set(cur.admins)` | 管理员只能增删普通成员，不能改群主、不能改管理员集合、不能自我提权 |
| 6 | 本地名单为空时，直接信任带外分发的创始名单 | 信任锚起点 |

由规则 5 得出：任命与撤销管理员只有群主可做；群主转移属于规则 4 的范围，是群主密钥失效前唯一的自救手段。

> **现状**：[已实现]（`roster.py` 的 `Roster.accepts()`），六条规则均有自检与单测覆盖。
> 补充一条实现细节：规则 3 的签名验证用**新名单**声明的 `owner`/`admins`，
> 再对 `cur` 复核签发资格 —— 因为规则 5 强制管理员集合相等，两条路径等价。

### 5.3 并发签名与冲突

规则 2 保证一份名单只有一个直接后继。两名管理员同时签发不同后继时，二者 `prev` 与 `version` 相同。处理方式：**同版本、同 `prev` 时按名单哈希的字典序取较小者**。该规则是确定性的，各节点无需通信即可收敛；被丢弃的一份需要重新签发。

> **现状**：[已实现但无调用方]。`roster.py` 的 `pick_concurrent()` 与 `content_hash()` 都在，
> 但目前没有任何运行时路径会同时持有两份并发候选（本地只维护一份 `roster.json`），
> 该函数只被自检与单测调用。等 §5.7 的自动分发落地后才会真正被使用。

### 5.4 宽限策略

**软件不做版本强制。** 具体为：

- `expires` 为**提示字段**，到点不阻断通信；
- 版本号仍单调递增并写入名单，但节点不因对方名单较旧而拒绝连接；
- 界面提示「你的名单已过期 N 天 / 与对方名单不一致」，由团体自行协调。

需要写明的后果：**移除成员的有效窗口没有上界**。被移除者与已更新名单的节点无法握手，但与尚未更新的节点之间仍可通信，直到后者更新。该窗口由团体协调解决，软件不额外施加机制。

> **现状**：[部分]。"不因对方名单旧而拒绝连接"已实现（握手只查在册，不查版本与过期），
> "本机名单已过期 N 天"已提示；但**"与对方名单不一致"永远算不出来** ——
> 界面传入的对端名单恒为 `None`（因为线上根本不交换名单，见 §5.7），
> 该分支只有在名单开始随协议分发之后才有意义。

### 5.5 解散

解散是一条独立于名单的通告记录：

- 签名者必须是当前名单中的 `owner`，管理员签发的通告无效；
- 通告携带高于当前名单的版本号；
- 成员收到后停止使用该团体，**保留本地数据，不删除**；
- 无中心系统无法技术强制解散，该通告的实际效果是「有共识的终止」；已分发到成员设备上的数据无法回收。

> **现状**：[未实现]。记录类型、签名校验、版本要求、处理路径、API 与界面都没有；
> 仅 `records.py` 的模块注释把"解散通告"列为四类记录之一。属 §16 P2。

### 5.6 群主密钥边界

群主密钥丢失等于该团体永久无法再管理（不能加人、不能删人、不能解散）。无中心系统没有恢复机制，唯一的缓解手段是群主在密钥仍有效时主动签发包含新 `owner` 公钥的名单完成转移。该限制需要写进使用说明。

> **现状**：[部分]。
>
> - 内核支持签发任意 `owner` / `admins` 的名单（规则 4），CLI 提供
>   `roster transfer` / `promote` / `demote`。
> - **插件与 GUI 没有这些操作**：`add_member()` 写死 `owner_key` 与 `admin_keys`
>   为当前值，界面上既不能转移群主也不能任免管理员。
> - **使用说明仍未写**：这条限制目前只存在于本文档与实现路径文档的"未回答问题"里。

### 5.7 名单分发（v0.2 明确为一等需求）

名单是**带外**建立信任锚的（规则 6），但之后的更新必须能到达成员端，否则"成员停在旧名单"
会表现为"新成员连不上任何人"（实现路径文档 §5.10 记录了这次真实故障）。

设计要求：

- 分发通道**不必**可信：名单自带签名，中转方无法篡改内容，只能拒绝服务；
- 首选载体是 §7 的注册表：任一在线节点都能提供完整快照，成员拉取后按规则 1/2 验证；
- 界面必须给出"本机名单版本 / 对方名单版本"的对照，冲突时明确提示重新获取；
- 邀请串（`gm1:`）保留为**首次加入**与**兜底**手段，不再是唯一手段。

> **现状**：[部分]，只有手动带外：
>
> - 安装路径是"群主把新的 `gm1:` 邀请串发给每个人"，界面上那个入口叫「加入 / 更新团体」；
> - 协议里没有任何 roster 消息动作（`transport.py` 的 `FEATURES` 含 `roster-v1`
>   但无消费者），`node.py` 的名单只用于本地授权；
> - 因此成员必须手工收串，且"与对方名单不一致"无法判定（见 §5.4）。
> - 属 §16 P2。

## 6. 共享项与权限

### 6.1 结构

```json
{
  "node":     "<设备公钥>",
  "owner":    "<属主主体公钥>",
  "share_id": "<该设备内的共享标识>",
  "seq":      3,
  "acl": {
    "read":  "group",
    "write": ["<主体公钥>"]
  },
  "sig": "<设备私钥签名>"
}
```

`read` 与 `write` 两项取值均为 `"owner"`、`"group"` 或主体公钥数组。

**修订（v0.2）**：

- **`path` 不再出现在签名声明里**。声明是发给全体成员的元数据，把宿主机目录结构写进去
  等于免费泄露；本机路径只保存在本机的 `LocalShare` 里（`shares.py`），
  不参与签名也不对外发送。

> **现状**：[已实现]（`shares.py` 的 `ShareDeclaration` / `LocalShare`）。

### 6.2 权限档位

只有两档：

| 档位 | `read` | `write` |
| --- | --- | --- |
| 只读 | 授予对象 | `"owner"`（等于无人可写） |
| 可上传 | 授予对象 | 授予对象 |

`write: "owner"` 的含义是"除属主外无人可写"——属主在自己机器上写入不经过协议。

**写权限的唯一语义是"只能新增，不能减少"**（可加性）。由此产生的行为必须写清：

- 共享项内容只增不减，容量上限因此成为唯一的磁盘边界（§6.5），不是可选项；
- 授权判定只看 ACL，**不记录 `created_by`**：写权限是"能不能新增"，与"谁传的"无关。

> **现状**：[已实现]。`Acl.allows()` 支持 `owner` / `group` / 公钥数组；
> 实现侧与上表的收敛见 §16 P1 第 4 项。

### 6.3 判定位置

判定在**属主设备**上执行。客户端隐藏按钮不构成授权；判定依据是发起方主体的公钥，该公钥来自握手，不接受请求参数中的自称身份。

> **现状**：[部分]。
>
> - 协议侧已实现：`node.py` 的 `_authorizer(peer)` 用 `peer.principal_key` 与
>   `roster.contains_principal()` 构造 `Authorizer`，请求参数里的任何身份字段都不参与。
> - **本机 HTTP 侧没有主体**：`/api`、`/file`、`/thumbs` 目前只校验单一令牌，
>   没有"凭据 → 主体"的映射，也没有每请求的主体上下文（§12 第 1/2/3 项）。
>   因此插件里所有涉及主体的判定都以**本机主体**为准（例如 `add_member()` 用本机
>   主体私钥签名，再由名单规则复核角色）——"本机身份即操作者"是当前的权宜之计。
> - 与 §12 的相互作用：物化到本机的远端字节落在本机的 HTTP 数据路由上，
>   而那里没有主体概念；换句话说，**能访问本机 HTTP 的进程可以读到已物化的远端内容**。
>   在 §12 补齐之前，物化缓存属于"本机可信域"，不应被当成跨主体隔离来依赖。

### 6.4 写入语义（上传）

写入是**可加**权限（§6.2）落到磁盘上的规则。传送一个文件分五步：

1. **定位**：发起方给出共享标识与相对路径（可带子目录），对端解析成本机绝对路径，
   越界与符号链接逃逸一律拒绝（§6.5）；
2. **探询**：先问对端"这个目标已经收下多少字节"（`probe`，走 write 权限 ——
   上传方可能只有写权限），据此决定续传起点；
3. **暂存**：分块写进 `<目标>.part`，**不碰目标文件**；每个分块都带"已经收下的
   字节数"，对端核对（不符就回 `offset_mismatch`），两个上传方抢同一个目标不会拼出垃圾；
4. **提交**：最后一个分块带 `eof` 标记，对端在这一步才把 `.part` 原子改名成目标文件；
5. **覆盖策略**：目标已存在时**默认拒绝**，只有发起方显式要求覆盖才替换 ——
   写权限是"只能新增"，覆盖等于让属主少一份内容，不能由上传方默认决定。

**必须在界面上做到的两件事**（否则大文件不可用）：

- **进度**：上传在后台线程里跑，`upload_remote` 立刻返回 `task_id`，界面轮询
  `upload_status` 显示"已传 / 总量 / 百分比"；
- **取消**：`cancel_upload` 在**分块边界**生效。取消不清除对端已收下的字节 ——
  它就是下次的续传起点（协议里没有远程删除，这也是刻意的），因此取消的代价是
  "少传一点"，不是"白传一遍"。

**续传的正确性条件**（三条缺一不可，否则从头传）：本机有该目标的记录、记录与**当前**
本地文件的 (大小, mtime) 一致、对端暂存字节数与记录一致。拿一份对不上的 `.part`
去续，产出的是拼接垃圾且没人会发现。

三条由此产生的行为必须写清：

- **断线不会毁掉已有文件**：没提交的上传只会在属主磁盘上留下 `<目标>.part`；
- **容量上限仍然生效**：判定按"共享项存量 − 本次丢弃 + 本次已写入"推算，基线在
  一次上传开始时量一次（每个分块都遍历一遍共享根会让大文件上传不可用）；
- **落点只由属主设备决定**：发起方只提交相对路径，不提供重命名与移动（§6.5）。

> **现状**：[已实现]。协议 `write` 支持 `part` / `offset` / `eof` / `overwrite` / `probe`；
> `client.push_file()` 是标准上传路径（CLI `put` 与插件 `upload_remote` 都走它），
> 带 `progress` 与 `cancelled` 回调；插件提供 `upload_remote` / `upload_status` /
> `cancel_upload` 三个 API 与界面入口，续传记录落在 `<数据根>/uploads.json`。
> 唯一还没做的是**上传过程中刷新页面仍能看到进度**（任务表在内存里，插件重载即失）。

### 6.5 安全边界

共享面是数据投放面：被授予写权限的主体可以在属主目录内创建任意文件。必须实现：

- 严格路径校验，禁止越界与符号链接逃逸；
- 按共享项的容量上限（授予写权限等于允许对方占用磁盘）；
- 共享目录与程序目录、配置目录分离；
- 不提供远程重命名与移动。

> **现状**：[已实现]。
>
> | 约束 | 位置 |
> | --- | --- |
> | 越界与符号链接逃逸 | `node.py` 的 `resolve_in_share()`：`realpath` + `commonpath`，跨盘符直接拒绝 |
> | 容量上限 | `node.py` 的 `_op_write()` 写入前按投影占用判定；`shares.py` 的 `DEFAULT_MAX_BYTES` |
> | 共享根与程序/身份目录分离 | `main.py` 的 `add_share()` 拒绝 data_root 与身份目录之内的路径 |
> | 无重命名/移动 | 协议 op 表里没有这类操作 |
> | 单次写入大小 | `node.py` 的 `MAX_WRITE_BYTES`（分块上传，避免单帧过大） |

## 7. 注册与发现

### 7.1 注册记录

```json
{
  "device":  "<设备公钥>",
  "seq":     7,
  "endpoints": [["240e:xxxx::1", 18443]],
  "shares":  ["<共享标识>"],
  "ts":      1767225600,
  "sig":     "<设备私钥签名>"
}
```

> **现状**：[已实现]（`registry.py` 的 `Registration`）。

### 7.2 与名单解耦

| | 签名者 | 变更频率 | 内容 |
| --- | --- | --- | --- |
| 团体名单 | 群主或管理员 | 低频（成员增删） | 主体、角色、设备公钥 |
| 注册记录 | 设备自己 | 高频（开关机、地址变化） | 设备公钥、当前端点、共享清单、序号 |

注册是**成员自助**行为，不需要管理员参与，因此成员的开关机不影响团体管理。

> **现状**：[已实现]。插件在节点启动后自动发布注册记录，端点集合变化时递增 `seq` 重发。

### 7.3 同步方式

注册记录是小数据集：按 200 台设备估算，约 20～40 KB。因此**不使用 DHT**：

- 任一在线共享节点都能提供完整快照；
- 新上线设备拉取一次快照，之后按 `seq` 比对做增量同步；
- 记录带设备自身签名，中继方无法伪造内容。

> **现状**：[部分]。
>
> - 快照的取用与合并已实现：`node.py` 的 `_op_registry()` 支持 `list` / `push`，
>   `registry.py` 的 `merge()` 按设备逐条比对 `seq`（严格大于才采纳，防回滚与重放），
>   插件的 `list_peers()` 并行向多个候选端点拉取并合并。
> - **缺"游标式增量"**：协议没有 `since` / `from_seq` 参数，所谓增量是"整表传输 + 本地按
>   seq 合并"。按 §7.5 的规模估算这不成问题，但设计措辞应与实现一致：
>   当前是**整表快照 + 按 seq 去重**，不是请求侧增量。

### 7.4 地址变化与稳定地址

- 监听套接字与注册记录中的端点必须使用**稳定地址**（EUI-64 或 RFC 7217 stable-privacy），不使用 Windows 默认启用的 RFC 4941 临时地址，后者会轮换；
- 定期比对本机全球单播地址集合，变化则递增 `seq` 并重新发布；
- Windows 防火墙默认阻止入站，需要为监听端口添加规则（需管理员权限，一次性）。

> **现状**：[部分]。
>
> - **稳定地址判定未实现**：`registry.py` 的 `local_addresses()` 只排除回环、链路本地、
>   多播、未指定；Python 标准库拿不到"这是不是 RFC 4941 临时地址"。实测中 Windows 侧
>   确实同时存在稳定地址与临时地址，因此在未显式 `--bind` 时两者都会被写进注册记录。
>   收敛路径：显式 `--bind`（当前可用的规避手段）；Windows 上用 `GetAdaptersAddresses`
>   的 `Temporary` 标志识别；或改用 RFC 7217 地址并只发布它。
> - **端点集合变化重发已实现**：`_refresh_own_registration()` 在地址集合变化时递增 `seq`；
>   代价是旧端点在被替换前会被对端白试一次。
> - **不按网段筛端点**：实测 Radmin VPN 网卡地址对同为该 VPN 成员的设备可用，按网段筛
>   会误删合法端点；可达性只能靠连接侧逐个尝试（已实现逐个尝试全部端点）。
> - **防火墙只有提示**：启动失败时按平台与错误码给出文案，不代替用户提权、不代加规则。

### 7.5 容量核算

| 对象 | 规模估算 | 结论 |
| --- | --- | --- |
| 成员记录 | 50 人约 4 KB | 无压力 |
| 设备记录 | 200 台约 20 KB | 无压力 |
| 名单全量 JSON | 约 25 KB | 无压力 |
| 一次成员变更的全量分发 | 25 KB × 200 节点约 5 MB | 可忽略 |

## 10. 传输与内容寻址

> **现状**：[未实现]。当前实现是 **offset/length 分块**（默认 256 KiB）+
> 远端物化（§15），不是内容寻址；两者可以并存，但设计目标里的"任意持有者提供任意块"
> 与"做种"都不存在。BitTorrent 相关依赖确实没有引入。

### 10.1 分块与寻址

成员之间的文件传输使用内容寻址的分块协议：文件切分为固定大小的块，每块以哈希标识，接收方可从任意持有者获取任意块。该设计复用 §7 的注册表作为来源目录。

### 10.2 做种

任何成员可以把已获取的内容保留并继续提供。这是可选项，用于实现「只要有一台机器没关机，资源仍可访问」。默认行为是内容仅由属主设备提供，属主离线即不可访问。

### 10.3 与 BitTorrent 的差异

不集成完整 BitTorrent：peer 发现已由 §7 提供，tracker 与 DHT 属于重复建设；引入 `libtorrent` 还会带来打包体积与 `HIDDEN_IMPORTS` 的额外成本。

### 11.2 轻客户端（Android，预留）

| 角色 | 能力 | 平台 |
| --- | --- | --- |
| 完整节点 | 持有名单、可作为共享节点提供服务 | Windows、Linux |
| 轻客户端 | 只有身份密钥；可读取共享内容、传输文件 | Android（首版不实现） |

首版只需在协议中预留该角色：角色字段加能力声明，不预留具体接口。协议不假设每个参与者都承担存储与转发。

> **现状**：[未实现]。注册记录、共享项声明与握手 hello 都没有角色或能力字段
> （`transport.py` 里的 `role` 是名单角色 owner/admin/member，不是本条所说的节点形态）。

### 11.3 本地网关

轻客户端的形态是在客户端内部运行一个仅监听 `127.0.0.1` 的 HTTP 服务：

```
[WebView] --http://127.0.0.1:port--> [本地网关] --团体加密通道--> [共享节点]
```

WebView 加载 `http://127.0.0.1:<端口>/`，页面内的 `/api`、`/file`、`/thumbs` 请求由网关经加密通道转发。三点作用：

1. `127.0.0.0/8` 属于 potentially trustworthy origin，WebView 无需证书即为安全上下文，麦克风可用；
2. 前缀变化、证书重签、`iPAddress` 匹配均不涉及；
3. 不存在第二套账号。

代价是网关需要正确转发 Range 请求，否则媒体播放会退化为整文件下载；Android 的明文流量策略需按目标版本确认。

> **现状**：[未实现]。壳自己的 `/file` 支持 Range（`send_file(..., conditional=True)`）
> 与按需取字节，但那是桌面端本机 Flask 服务，不是"WebView → 127.0.0.1 网关 → 加密通道"
> 那一层。

## 15. 已落地但原设计未描述的能力

本节记录实现过程中长出来、v0.1 设计里没有的能力。它们**已实现并有测试**，因此必须写进
设计文档，否则下一次读文档的人会以为代码跑偏了。

### 15.1 远端共享物化与按需取字节

- **物化**（`materialize_remote`）：在本地 `.cache/remote/<真实设备ID>/<共享标识>/` 造出与
  远端同形的目录树：目录直接建，文件先落 **0 字节占位**并写入**对端**的 `mtime`，
  同时写一份 `<共享标识>.index.json`（记录 `size` 与 `mtime_ns`）。
- **按需取字节**：读文件就是普通 HTTP 请求。壳的 `/file` 在根校验**之后**回调
  `is_content_placeholder()` / `ensure_file()`，由插件把字节取回本地。
  暂存文件走 `<cache>/staging`（与被替换目标同卷，`os.replace` 原子落位）。
- **对账**：重新物化时，对端删掉/改名的条目在本地删除；对端内容变化（`size` 或 `mtime_ns`
  任一不同）且本地已持有真字节时，丢掉本地字节退回占位。**达到条目上限（`truncated`）时
  绝不对账** —— 那时遍历结果只是一个子集。
- **为什么这样设计**：消费型插件（图片相册、播放器）是按本地路径工作的，
  物化成真实本地目录后它们无需理解协议。代价与边界见 `.dsh/group-mesh-materialize.md`
  §2.2（"要解码源文件"的消费方与 0 字节占位不相容；额外根的虚拟相对路径在 `/file`
  里只按第一根解析，是壳侧既有缺陷）。

### 15.2 一次性镜像

`mirror_share` 把远端共享项的内容**取回真字节**并落到指定本地目录（与物化相反：
物化只落目录结构与占位）。用于"我要一份离线拷贝"。

### 15.3 网络位置来源（壳共享组件契约）

设置面板里的目录选择器支持 **`placement: network-location`** 的插件扩展：
提供方声明 `embedUrl`，宿主用 `postMessage` 回填**本地目录**。
group-mesh 是参考实现（`get_extensions()` + `frontend/network-location.html`）：
用户在消费方插件的设置里选"网络位置"，即把远端的某个共享项取回到本地一个目录，
再把那个**本地目录**作为消费方的根。契约见 `docs/plugin-guide.md`。

**这不是** §12 第 4 项所说的"`get_file_roots()` 支持远端来源"：它是"把远端物化成本地"，
壳的文件路由始终只服务本机路径。两种方案并存时以本节为准。

### 15.4 地址交换

界面上可直接复制本机地址（`[2409:…]:19443` 形态），也可粘贴对方地址按设备更新端点
（手工端点登记作为发现失败时的兜底）；端点探测并行化并有整次预算。
`peers` 支持"按地址登记"与"按设备更新"两种高级入口。

### 15.5 节点自启与注册发布

插件加载后自动启动共享节点并发布注册记录；监听成功**之后**才发布（用真正绑上的端口，
设置里写 `0` 时端口由内核分配）；启动失败按 30 s 冷却重试而不是永久放弃；
名单在**每条连接**上重读，因此群主在别处加人后运行中的节点立刻认。

### 15.6 验证设施

- 多实例夹具（`tests/harness/`、`tests/test_multi_instance_fixture.py`）：一个进程内跑
  多个真实插件实例，用于物化/网络位置/取字节的端到端验证；
- 前端三层用例：纯渲染（桩 Bridge + 无头浏览器）、真实壳（起服务 + 导航 + iframe）、后端 API；
- 非无头演示脚本（`tests/debug_materialized_gallery.py`、`tests/debug_network_location.py`）：
  逐步截图，用于回答"肉眼才能回答"的问题。
